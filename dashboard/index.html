💡 What is an SCC?

A Strongly Connected Component is a maximal set of nodes where every node can reach every other node by following directed edges. On the web, this means a group of pages that all link back to each other.

Tarjan's algorithm finds all SCCs in a single DFS pass using discovery time and low-link values, running in O(V+E) time.

Size 1: No back-links (singleton)
Size 2–3: Small mutual cluster
Size 4–5: Medium community
Size 6+: Large interconnected hub

What is an SCC?

A Strongly Connected Component is a maximal group of pages where every page can reach every other by following links — a mutual cycle. If A→B→C→A, all three belong to the same SCC.

Tarjan's Algorithm

One DFS pass tracking discovery time and low-link value per node. When a node's low-link equals its discovery time, it's the root of a finished SCC. Pops the stack and records it. Runs in O(V+E).

What the graph tells you

Most of the web is gray singletons — pages nobody links back to. Colored clusters are tightly linked ecosystems (e.g. a docs site cross-linking all its pages). Larger cluster = stronger community cohesion.

Comparative Analysis of Graph Traversal Algorithms

BFS vs DFS vs Priority (Best-First) — same frontier class, three behaviours

BFS — Breadth-First O(V + E)

Explores the web level-by-level from the seed. Guarantees shortest hop count to each domain. Produces the most balanced, representative crawl of a site's neighbourhood.

Frontier: std::queue<URLEntry>
Order: FIFO — earliest discovered first
Space: O(V) — entire frontier in memory
Best for: broad coverage, short paths
DFS — Depth-First O(V + E)

Follows one link chain as deep as possible before backtracking. Useful for discovering deeply nested pages within a single domain. Memory-efficient for sparse graphs.

Frontier: std::vector<URLEntry> (LIFO)
Order: push_back / pop_back
Space: O(depth) — only active path
Best for: deep paths, limited memory
Priority — Best-First O(E log V)

Uses a max-heap keyed on a heuristic score. Trusted domains, keyword matches in URL path, depth penalty, and seed proximity all contribute to priority.

Frontier: std::priority_queue<URLEntry>
Order: max-heap on score ∈ [0, 1]
Space: O(V) + heap overhead
Best for: targeted high-quality pages
Metric BFS DFS Priority
Time complexity O(V + E) O(V + E) O(E log V)
Completeness ✓ Complete ✓ Complete ✓ Complete
Shortest path ✓ Guaranteed ✗ Not guaranteed ✗ Not guaranteed

Priority Queue — Best-First Crawling

Heuristic scoring replaces FIFO order with quality-guided exploration

Instead of a plain FIFO queue, the frontier uses a max-heap (std::priority_queue) keyed on a score in [0, 1]. Each URL is scored before enqueueing. The highest-scoring URL is always dequeued first, so the crawler naturally gravitates toward trusted, keyword-rich pages.

The trade-off vs. BFS: O(log V) per enqueue/dequeue instead of O(1), but with far higher signal-to-noise in the crawled pages.

// URLEntry max-heap ordering

bool operator<(const URLEntry& o) const {'{'}

return priority < o.priority; // reversed → max-heap

{'}'}

Scoring Signals (url_scorer.cpp)

Trusted domain match +0.40
Keyword in URL path/host +0.20
Reputable suffix (.edu .gov .org) +0.10
Seed proximity (depth ≤ 1) +0.05
Depth penalty (per hop) −0.10
URL length > 80 chars −0.10
Final score clamped to [0.0, 1.0]

Strongly Connected Components — Tarjan's Algorithm

Single-pass iterative DFS · O(V + E) · no recursion depth risk

Tarjan's algorithm finds all SCCs in one DFS pass by maintaining a discovery timestamp and a low-link value per node. When a node's low-link equals its discovery time after fully exploring its subtree, that node is the root of a complete SCC.

Our implementation uses an explicit call stack (vector of frames) instead of C++ recursion. This prevents stack overflow on large web graphs where recursive DFS would exceed the OS stack limit.

disc[v]

Discovery timestamp — monotonic clock, set once on first visit

low[v]

Minimum disc[] reachable from v's subtree via back-edges

on_stack[v]

Whether v is currently on Tarjan's auxiliary stack

SCC root

Detected when disc[v] == low[v] after subtree is done

// Iterative Tarjan — core loop

while (!call_stack.empty()) {'{'}

Frame& frame = call_stack.back();

int v = frame.node;


if (frame.child_idx < adj[v].size()) {'{'}

int w = adj[v][frame.child_idx++];

if (disc[w] == -1) {'{'} // tree edge

disc[w] = low[w] = timer++;

push w onto call_stack;

{'}'} else if (on_stack[w]) {'{'} // back edge

low[v] = min(low[v], disc[w]);

{'}'}

{'}'} else {'{'} // done with v

propagate low[v] to parent;

if (disc[v] == low[v]) // SCC root!

pop stack until v → emit SCC;

{'}'}

{'}'}

Topological Sort — Kahn's Algorithm on SCC DAG

Applied to the condensed DAG after SCC contraction · O(V + E)

After Tarjan's SCC, every SCC is contracted to a single super-node. The resulting condensed DAG is guaranteed acyclic — Kahn's BFS-based topological sort is then applied to order these super-nodes from sources (no incoming edges) to sinks.

We use Kahn's instead of DFS-based topo sort because: it's iterative (no recursion depth risk), and it detects cycles by checking output.size() == V.

// Kahn's algorithm

1. compute in_degree[v] for all v O(E)

2. enqueue all v where in_degree=0 O(V)

3. while queue not empty:

u = dequeue → append to order

for each v in adj[u]:

if --in_degree[v] == 0: enqueue(v)

4. if order.size() < V: cycle detected!

Pipeline: Crawl → SCC → Condensation → Topo Sort

Crawl → Domain Graph

2

3

SCC Condensation DAG · O(V+E)

each SCC → one super-node, inter-SCC edges preserved, self-loops removed

orders super-nodes; exported to topo_order.csv

String Matching — Knuth-Morris-Pratt (KMP)

Keyword search across all crawled page content · O(n + m) per search

KMP avoids redundant character comparisons by pre-computing a failure function (prefix table) for the pattern. On a mismatch, instead of starting over, it falls back along the failure links — guaranteeing O(n + m) total comparisons regardless of text or pattern content.

kmp_failure_function(p)

Builds prefix table. fail[i] = length of longest proper prefix of p[0..i] that is also a suffix. O(m).

kmp_search(text, pattern)

Counts all (possibly overlapping) occurrences. Uses fail table to skip on mismatch. O(n + m).

kmp_multi_search(content_map, keywords)

Searches K keywords across all domain → HTML content entries. Returns hit count + list of matching domains per keyword. O(K × Σ(nᵢ + mₖ)).

// Why KMP over naive search?

Naive: O(n × m) — tries every position

KMP: O(n + m) — never re-reads text chars

For a 100KB page with a 20-char pattern:

Naive worst-case: 100,000 × 20 = 2M comparisons

KMP: ≤ 100,020 comparisons guaranteed

Thread-Local Buffering — Lock-Free Storage

Each worker writes to its own buffer during crawl — merged once at the end

The naive approach — a single shared graph map with a mutex around every write — causes severe lock contention. With 8 threads each trying to write hundreds of edges, threads spend more time waiting on locks than crawling.

Our solution: each thread has a ThreadLocalBuffer (its own local_graph, local_visit_count, local_domains). During the crawl phase, threads never share any data structure. Once all threads finish, a single merge pass combines everything.

// StorageManager — thread-local writes

void add_page(int thread_id, ...) {'{'}

auto& buf = thread_buffers[thread_id];

buf.local_graph[domain] = links; // NO LOCK

buf.local_visit_count[domain]++;

{'}'}


// Single merge after all threads finish

void merge_all_buffers() {'{'}

for (auto& buf : thread_buffers)

UNION edges into link_graph; // once, no race

{'}'}

Synchronisation Points

pages_crawled — atomic<int>

Lock-free increment via fetch_add. Used as global stop condition.

URLFrontier — single mutex

One mutex guards enqueue + visited set. Batch_enqueue() acquires it once per batch — not once per URL — to reduce contention by ~N×.

URLScorer — per-thread instance

Each worker constructs its own scorer. No shared scorer state means zero lock contention for priority computation.

Storage writes — zero locks

thread_buffers[thread_id] is accessed only by thread thread_id. No mutex, no semaphore, no contention.
